## Item 9 — SAE reconstruction on a representative sequence

**Why:** v0.9.0 validated the SAE on a 4-token input ("The quick brown fox") — non-representative.
Baseline on file: recon_mse 3130, l0 1293, frac_alive 0.384 at layer 8.

**Setup:** `google/gemma-2-2b` (bf16) + `gemma-scope-2b-pt-res` `layer_8/width_16k/average_l0_71`
SAE, `sae_reconstruction` opted in, one step. Representative input ≥128 tokens of real prose.

**Metric:** `recon_mse`, `l0`, `frac_alive`, `ce_recovered_proxy` at layer 8.

**Baselines:** (a) the 4-token result above; (b) the SAE's named design point **l0 ≈ 71**.

**Hypothesis:** on a representative sequence, l0 drops from ~1293 toward ~71 and recon_mse drops
substantially. **If l0 does NOT approach ~71, that is the result** (do not tweak the input to
force it) — it would indicate a layer/dtype/fit issue worth recording.

**Result (2026-05-23, CPU — GPU was busy with another 10.4 GB process):** 189-token prose input
(the passage tokenized to 189 ≤ 256), one step, 59.27 s on CPU.

| metric | 4-token baseline (v0.9.0) | 189-token (this run) | SAE design point |
|--------|--------------------------:|---------------------:|-----------------:|
| recon_mse | 3130 | **83.5** | — |
| l0 | 1293 | **106.5** | ~71 |
| l1 | — | 959.7 | — |
| frac_alive | 0.384 | 0.487 | — |
| ce_recovered_proxy | — | −7.49 | — |

**Finding:** recon_mse fell ~37× (3130 → 83.5) and l0 fell from 1293 → 106.5 — into the right
ballpark of the SAE's `average_l0_71` design point, ~1.5× above it. The remaining gap is most
plausibly **bf16 activation noise** (gemma-scope SAEs are fit on fp32 residual activations; we
ran the model in bf16), with the specific passage and BOS-token activation also contributing.
Per discipline the input was **not** tuned to force l0 = 71; 106.5 is reported as-is.
`ce_recovered_proxy` is negative — flagged but not over-interpreted (it is an explicit proxy,
not the validation target). Conclusion: the 4-token v0.9.0 numbers were non-representative as
suspected; a representative sequence yields sane, near-design-point sparsity and low recon error.

**Bonus:** Gemma 2 2B is SDPA-default, so this run also fired the item-6 attach-time WARN
(`induction_score / attention_pattern_entropy requested but the model uses
attn_implementation='sdpa'`) — confirming that warning on a real model.

## Item 8 — induction_score + attention_pattern_entropy under eager attention

**Why:** SDPA (HF default) returns no per-head attention weights, so both diagnostics silently
emit zero tags. v0.9.0 never actually captured them. Item-6 added an attach-time WARN.

**Setup:** `Qwen/Qwen2.5-0.5B` via `smoke_hf_model.py`, run twice — `--attn-impl sdpa` (baseline)
and `--attn-impl eager`, both on `--device cuda`. Grep each `metrics.jsonl`.

**Metrics:** count of `activation/induction_score/*` and `activation/attention_pattern_entropy/*`
tags emitted; plausibility of values (induction_score ∈ [0,1] per head; entropy in nats > 0).

**Baseline:** the SDPA run (expect zero such tags).

**Hypotheses:** (1) SDPA emits zero induction/entropy tags AND fires the item-6 WARN in stderr;
(2) eager emits real per-head values. The SDPA WARN check is an end-to-end test of the item-6
warning on a real model (only unit-tested so far).

**Result (2026-05-23, CPU):** `Qwen/Qwen2.5-0.5B`, fp32, 4 steps, seqlen 32, every_n_steps 2.
Added `--attn-impl` + `--device` flags to `smoke_hf_model.py`. Two runs:

| run | item-6 WARN | induction_score tags | attention_pattern_entropy tags |
|-----|:-----------:|---------------------:|-------------------------------:|
| `--attn-impl sdpa` (baseline) | **fired** (×2: stock + filtered attach) | **0** | **0** |
| `--attn-impl eager` | not fired | **672** (24 layers × 14 heads × 2 emits) | **672** |

Eager value ranges: `induction_score` ∈ [0.000, **0.986**], mean 0.074; `attention_pattern_entropy`
∈ [0.000, 2.881] nats, mean 1.606 (max < ln(32)=3.47; 0 = attention-sink heads).

**Findings:** (1) Confirms the v0.9 capability — both diagnostics emit real per-head values only
under eager attention; under SDPA they silently emit nothing. (2) The max induction_score ≈ 0.99
means the synthetic repeated-token probe **detected a strong induction head** in Qwen2.5-0.5B
(meaningful regardless of the random main input, since the probe is self-contained). (3) **Item-6
WARN is now validated end-to-end on a real SDPA model** (previously only unit-tested with a fake
config) and correctly stays silent under eager.

## Item 10 — GPU performance budget (design.md §10)

**Why:** bench numbers were CPU-only; design.md §10 budget is ≤10% overhead on a synthetic 50M
model. The bench also (a) was CPU-only without CUDA sync, (b) named blocks `.blocks.N` so the
v0.9 lens/induction diagnostics no-op, (c) used `every_n_steps=200` over 100 steps (diagnostics
fire ~once).

**Setup:** `bench_50m.py` enhanced — `.layers.N` block naming (v0.9 diagnostics fire),
`--device cuda` with `torch.cuda.synchronize()` around timing, realistic `every_n_steps`.
Synthetic 50M model (apples-to-apples with §10). Real-model v0.9 cost is already on record
(Gemma 4 E2B +134% on CPU, v0.9.0).

**Metric:** overhead % = instrumented/baseline − 1, on GPU with synchronization.

**Baseline:** uninstrumented run, same model/steps, same device.

**Hypothesis:** overhead within or near the ≤10% §10 budget at a realistic emission cadence;
report honestly if the v0.9 diagnostics push it over.

### Side-finding (GPU bring-up surfaced shipped bugs)

Bringing the bench up on GPU surfaced **GPU device-correctness bugs in three shipped `core/`
primitives** — they built CPU index/edge tensors and combined them with CUDA inputs:
`weight.singular_values` (CPU `randperm` → `index_select` on a CUDA matrix — hard crash),
`attention.induction_score` (CPU `arange` indices on a CUDA attn tensor — crash), and
`spectral.esd` (CPU `linspace` edges returned alongside CUDA `histc` counts — inconsistent).
Fixed by propagating `.device` (no `.cuda()`; invariant #4 preserved) + 3 CUDA-skipif regression
tests. Item 8 only passed earlier because it ran on CPU. Separate commit `fix(core)`.

**Result (2026-05-23, GPU RTX 5080, synthetic 88.1M model, stock `llm` recipe):**

| config | baseline | instrumented | overhead |
|--------|---------:|-------------:|---------:|
| every 25 steps, 100 steps (×4 emits) | 1.37 s | 17.80 s | **+1202%** |
| every 100 steps, 100 steps (×1 emit) | 1.37 s | 5.56 s | +306% |
| every 125 steps, 500 steps (×4 emits) | 6.38 s | 22.80 s | +257% |

**Finding:** per-emission cost is **~4.1 s** and roughly constant across configs (1 emit = 4.19 s;
4 emits = 16.4 s ≈ 4.1 s each), so cuSOLVER init is **not** the dominant factor — the SVD-based
weight diagnostics (`effective_rank` / `stable_rank` / `heavy_tail_alpha` / `sv_histogram`, all via
`torch.linalg.svdvals` over ~80 weight matrices) genuinely cost ~4.1 s per emission on this 88M
model. A single GPU training step is ~0.0137 s, so **one emission ≈ 290 training steps' worth of
compute**. The **≤10% §10 budget is NOT met on GPU at aggressive cadences** — it was conceived on
CPU (~15% at v0.8), where the training step is far slower so the same SVD cost is a small fraction.
To stay ≤10% on this GPU you'd need `every_n_steps` ≳ 3000. On CPU the budget still holds.
This is a real negative result: the fixed SVD diagnostic cost doesn't shrink on GPU while the
training step does, so the *ratio* explodes. Note: `induction_score` / `attention_pattern_entropy`
no-op on the synthetic model (no per-head attn weights) — their cost here is only the shared probe
forward pass.

### Fix applied (2026-05-23) — share the SVD across diagnostics

Profiling (`/tmp/profile_svd.py`) found the SVD was computed **4.0× redundantly**: `effective_rank`,
`stable_rank`, `heavy_tail_alpha`, and `sv_histogram` each called `singular_values(W)`
independently (1043 ms once vs 4232 ms ×4; post-SVD math only 8.5 ms). Fixed by computing the SVD
**once per matrix per step** in the recorder (`_sv` cache keyed by `id`) and feeding `_from_sv`
variants of the primitives. Result:

| config | before | after | speedup |
|--------|-------:|------:|--------:|
| every 25 steps, 100 steps | +1202% | **+306%** | ~4× |
| every 100 steps, 100 steps | +306% | **+78.6%** | ~4× |

Per-emission cost ~4.1 s → ~1.08 s. The budget now holds at realistic cadences (`every_n_steps`
≳ 800 vs ≳ 3000 before). Helps CPU equally. Remaining headroom (lower `max_dim`, eigvalsh on the
Gram matrix) left as a separate future optimization — kept in TODO.md.
