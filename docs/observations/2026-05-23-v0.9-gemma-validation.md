### SDPA limitation: induction_score and attention_pattern_entropy not captured

Gemma 4 E2B (like Gemma 2 2B) uses SDPA attention by default. SDPA does not return
per-head attention weight tensors even when `output_attentions=True` is requested — the
transformers framework emits a warning and silently ignores the flag. Both dispatchers rely
on capturing `hook_out[1]` from self_attn forward hooks, which expects a
`(hidden_states, attn_weights, ...)` tuple. Under SDPA, `hook_out` is a single tensor
(hidden states only), so `captured` remains empty. No metrics are written and no exception
is raised.

**Impact on v0.9.0:** `induction_score` and `attention_pattern_entropy` are non-zero in
unit tests (which use a custom `_Attn` stub that returns a proper tuple), but they produce
zero tags on any production HF model that defaults to SDPA. Callers can work around this
by passing `attn_implementation="eager"` to `from_pretrained`, which re-enables attention
weight materialization. This is a known SDPA limitation, not a circuitry bug; it will be
documented in the v0.9.0 release notes.

### Wall-clock delta vs v0.8

The +134% increase (39.6 s → 92.74 s) for 1 step is explained by the three new activation
diagnostics:
- `logit_lens_kl`: one matrix multiply per hooked block output per step. Gemma 4 E2B with
  `model.language_model` prefix hooks 35 block outputs × 5 activation sources = 175 KL
  computations.
- `induction_score`: issues a second full forward pass (the induction probe) per step.
  The probe pass on a 5.1B model on CPU is the dominant cost.
- `attention_pattern_entropy`: injects `output_attentions=True` globally; under SDPA the
  injection is a no-op (no overhead).

Users who do not need `logit_lens_kl` or `induction_score` can remove them from
`activation_diagnostics` via `Recipe.with_prefix(...).with_sae(...)` + `dataclasses.replace`
or wait for a per-diagnostic `enabled` flag (v0.10 candidate).

### Dispatcher fix: logit_lens_kl on multimodal models

During validation, `logit_lens_kl` crashed on Gemma 4 E2B with:

```
ValueError: logit_lens_kl: unembed shape (262144, 1536) has no dim matching d_model=6144
```

Root cause: `ctx.activations` contains outputs from all hooked modules, including
`down_proj` INPUT activations (MLP gate tensors) which on Gemma 4 have `d_model=6144`
(the MLP intermediate width). The dispatcher's `final_logits` computation used the wrong
tensor to derive `d_model` and then called `_llk` on an incompatible tensor.

Fix applied in this commit: filter `ctx.activations` to entries whose `last-dim` matches
the unembed's d_model dimension before computing `final_logits` and iterating. For Gemma 4
E2B, this correctly retains only the 1536-dim residual-stream activations (35 block outputs
+ 4 × 35 other residual-dim activations = 175 entries) and discards gate/intermediate
activations of other widths.

### Dispatcher fix: logit_lens_kl layer sort order

The initial implementation sorted `ctx.activations` lexicographically. Module name
`layers.9` sorts after `layers.34` because `'9' > '3'` byte-wise, so `block_outputs[-1]`
was `layers.9.self_attn` instead of the actual final layer. The reference distribution
(`final_logits`) was computed from layer 9's output; all KL values measured divergence
from layer 9, not from the model's final prediction distribution. KL of the reference
tensor with itself is 0, confirmed by `layers.9.self_attn = 0.000`.

Fix applied: sort by `(_layer_idx(name), name)` where `_layer_idx` extracts the numeric
layer index via `re.search(r'\.layers\.(\d+)(?:\.|$)', name)`. This ensures `layers.9`
sorts before `layers.34` regardless of digit count.

### Short-sequence caveat

The prompt "The quick brown fox" has 4 tokens. The `gemma-scope-2b-pt-res` SAE was trained
on `monology/pile-uncopyrighted` with context_size=1024 and BOS prepended. The l0 figure
(1292 vs expected ~71) and negative `ce_recovered_proxy` reflect out-of-distribution
activation statistics on an extremely short, non-representative input. Re-running on a
realistic paragraph-length prompt would yield l0 and reconstruction quality closer to the
published Gemma Scope benchmarks.

### SAE overhead is near zero on one step

The 71.86 s vs 72.35 s comparison shows that adding a SAE encode+decode at layer 8
contributes negligible wall-clock overhead relative to the full model forward pass.
This is expected: at 2304 × 16384 (gemma-2-2b residual dim × SAE width), the SAE is
a small fraction of the 2B-parameter model's total FLOP budget. The overhead will be
more visible at batch sizes > 1 or with many SAE hooks.

## Bugs found and fixed in this validation run

1. **logit_lens_kl dispatcher crashed on multimodal models** (Gemma 4 E2B): see above.
   Fixed in `src/circuitry/recorder/live.py`. Tests still pass (194 / 194).
2. **SAE release name:** `scripts/v09_sae_validation.py` originally used `"google/gemma-scope-2b-pt-res"`
   as the SAE release name, which `sae_lens` treats as a raw HF repo_id (looking for `cfg.json`)
   rather than the registered release key `"gemma-scope-2b-pt-res"`. Fixed in the script.
3. **Stale `torch_dtype` kwarg:** `scripts/v09_sae_validation.py` used `torch_dtype=` which is
   deprecated in transformers 5.x; updated to `dtype=`.
4. **logit_lens_kl sort order bug:** Lexicographic sort placed `layers.9` after `layers.34`,
   causing `final_logits` to be computed from layer 9's output instead of the true last layer.
   Fixed in `src/circuitry/recorder/live.py` by sorting on numeric layer index extracted via
   `re.search(r'\.layers\.(\d+)(?:\.|$)', name)`. All per-layer KL values in this document
   reflect the corrected sort order.
